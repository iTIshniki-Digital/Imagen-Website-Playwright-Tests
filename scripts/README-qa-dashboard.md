# QA Dashboard — разовая настройка

Дашборд: https://claude.ai/artifact/4vmBWLsZUtj8W7GTcpCQje ("Imagen QA Runs")

Форма на сайте (wordpress-plugin/) в этой схеме больше не участвует —
запуск тестов идёт полностью через GitHub (issue → Actions). Сам плагин
оставлен рабочим на сайте (можно деактивировать, когда будет удобно — это
действие на сайте, его делаете вы), но дашборд его больше не открывает.

## Как это работает

1. Вкладка **Run Tests** в дашборде → настройки → **"Open on GitHub"** —
   открывает новый GitHub issue, уже заполненный (заголовок + тело с
   блоком `` ```qa-run ``` `` внутри), с лейблом `qa-run`.
2. Вы (или клиент, если ему дали доступ к репозиторию) просто жмёте
   **Submit new issue** на GitHub — никаких дополнительных действий.
3. Workflow `.github/workflows/qa-issue-trigger.yml` ловит открытие этого
   issue, разбирает блок `qa-run`, проверяет значения (тот же белый
   список браузеров/путей/фильтра, что был в форме) и запускает
   `playwright.yml` — если что-то невалидно, вместо запуска пишет причину
   комментарием в тот же issue.
4. Когда прогон закончится, `scripts/sync-qa-github-issues.js`
   (отдельный шаг в `playwright.yml`) комментирует итог в исходный issue
   и закрывает его, а на каждую упавшую проверку заводит/обновляет issue
   с лейблом `qa-bug` (скриншот и видео — прямо в теле issue, GitHub сам
   их показывает по ссылке, не нужно ничего прикреплять руками). Когда
   проверка снова проходит — соответствующий `qa-bug` issue закрывается
   автоматически с комментарием "Fixed".
5. Сам дашборд (красивый общий вид — категории, статусы, история) по-
   прежнему наполняется отдельно: попросите Claude **"синхронизируй
   QA-дашборд"** после прогона — он заберёт `latest.json` и
   скриншоты/видео с Google Drive и запишет в дашборд (подробности ниже,
   раздел "Как синк работает на самом деле"). GitHub Issues и сам
   дашборд — два независимых, не блокирующих друг друга способа увидеть
   результат; не обязательно пользоваться обоими.

## 0. Включить права записи для GitHub Actions (обязательно, один раз)

Без этого шага ничего из выше описанного не заработает — Actions упадёт с
403 на попытке завести/закрыть issue или запустить другой workflow.

Repository → **Settings → Actions → General → Workflow permissions** →
выбрать **"Read and write permissions"** → Save.

(Сами воркфлоу уже просят ровно то, что им нужно, через `permissions:` в
YAML — но репозиторий должен разрешать выдавать write вообще, это
отдельный переключатель.)

## 1. Создать фиксированный файл latest.json на Drive

1. Откройте ту же папку Google Drive, куда уже падают отчёты (куда
   указывает секрет `GDRIVE_FOLDER_ID` в GitHub).
2. Создайте в ней пустой файл с содержимым `{}`, назовите `latest.json`.
3. Скопируйте его id из адресной строки:
   `https://drive.google.com/file/d/`**`ВОТ_ЭТОТ_ID`**`/view`.
4. GitHub → репозиторий → Settings → Secrets and variables → Actions →
   New repository secret → имя `GDRIVE_LATEST_JSON_FILE_ID`, значение —
   этот id.
5. Тот же id вставьте в сам дашборд: вкладка Run Tests → Dashboard
   settings → "Google Drive file ID (latest.json)" → Save settings
   (нужны права Editor на артефакт).

Google API-ключ создавать не нужно — файл публичный ("anyone with the
link"), Claude читает его обычной ссылкой, без ключей и авторизации.

## 2. Доступ клиента к репозиторию

Чтобы клиент мог сам открывать issue и запускать прогон — обычный доступ
коллаборатора к этому репозиторию (Settings → Collaborators and teams →
Add people). Выбрано: доступ в этот же репозиторий, без отдельного
"тонкого" репо-прокладки — проще в настройке, но учтите: с ролью Write
клиент увидит и остальной код репозитория (не только тесты), а Write —
по умолчанию минимальная роль, которая даёт запускать workflow_dispatch
руками через UI; наш issue-триггер на это не завязан (работает и с Read,
раз человек просто открывает issue), но сам человек может параллельно
зайти и в Actions.

## Дальше само

- **Open on GitHub** в дашборде → Submit issue на GitHub → готово, прогон
  запущен. Прогресс видно во вкладке Actions репозитория.
- Результат и баги появляются **в самом GitHub** автоматически — никого
  не нужно просить.
- Попросить Claude **"синхронизируй QA-дашборд"**, если хочется увидеть
  тот же результат в красивом виде на claude.ai (категории, история,
  общая картина) — не обязательно, GitHub Issues работают сами по себе.
- Категории — категории ручного чек-листа клиента (дашборд
  `marketing-server/services/qa-dashboard`), слово в слово. Список должен
  совпадать в ТРЁХ местах: `scripts/qa-dashboard-categories.js`,
  `wordpress-plugin/imagen-qa-test-runner.php` (`imagen_qa_scopes`,
  сейчас не используется для запуска, но держим на всякий случай) и
  константа `CATEGORIES` в самом дашборде (его HTML). Поменяли один —
  поменяйте все три.

## Как синк дашборда (не GitHub Issues, а claude.ai-страницы) работает на самом деле

Страница claude.ai Artifact не может сделать `fetch()`/XHR ни на один
внешний хост — ограничение песочницы, не баг. Поэтому результаты туда
кладёт Claude, когда его просят ("синхронизируй дашборд"):

1. Читает `latest.json` с Google Drive по публичной ссылке (без ключей —
   `scripts/fetch-qa-dashboard-run.js <file-id>` скачивает и его, и все
   скриншоты/видео упавших проверок локально).
2. Каждый файл грузит в хранилище ассетов самого артефакта (Artifact
   `action: "upload_asset"`) — так они отдаются с того же домена, что и
   сама страница (внешний `<img>`/`<video>` тоже заблокирован
   песочницей).
3. Пишет прогон в `runs`, заводит/закрывает баги в `bugs`, обновляет
   `meta/sync` — через Artifact `action: "write_db"`.

Руками в браузере по-прежнему работает: завести баг вручную (вкладка Open
Bugs, можно сразу приложить файл — идёт через `assets`, не внешний
fetch), отметить баг исправленным/снова открытым, полистать историю.
